Receipt line items

Receipts are the first use of something more general: agents can define their own data on top of the ledger, and the platform guarantees it stays consistent with the money. Nothing here is specific to a country or to receipts. Receipts are just the first template.

Recommendation: don't build a receipts subsystem. Upgrade the existing user tables (db_*) with ledger-aware column types, unique keys, references, row checks, a "rows must add up to the entry" constraint, and an atomic multi-table write. Then ship a receipts template that uses all of it. Dashboards already read table:<id> sources, so analytics comes almost for free.

Schema primitives (country-agnostic)

Column types: existing, plus new ones

TypeStored as / validated

Each column can also carry description, required, enum and pattern.

Table-level guarantees

{ name, description,                      // descriptions are what the next agent reads
  columns: [...],
  keys:   [["merchant","store_code"]],      // unique; enforced by a Mongo unique index, so it is safe under concurrency
  checks: [{ expr: "row.qty * row.unit_price ... ", message: "...", level: "error"|"warn" }],
  ledger: { entry: "entry", amount: "amount", accounts: ["expenses:"] }   // Σ amount per entry = that entry's postings in those accounts
}
  • The ledger constraint is the one that matters. Line items, invoice splits and trip allocations all mean "these rows explain this entry". It is checked for every entry a write touches. A reversed entry is exempt, and its rows are marked entry.effective=false.
  • Checksum functions in CEL: gtin_valid, iban_valid, luhn, mod11_10 (the Croatian OIB), mod97. The platform stays generic, and an agent adds row.country != "HR" || mod11_10(row.tax_id) as a check when it learns a country's rule.

Atomic multi-table write: db_batch

A receipt is a store, a header and 30 lines. Written one call at a time, the "items add up" rule could never pass partway through. One call does it all:

db_batch {
  dry_run?: true,
  ops: [
    { db: "stores",        upsert: { row_id: "HR:12345678903:P1232", cells: {...} } },
    { db: "receipts",      upsert: { row_id: "01M6AVWD…", cells: {...}, version?: 2 } },
    { db: "receipt_items", delete_where: "row.entry == '01M6AVWD…'" },
    { db: "receipt_items", upsert: { row_id: "01M6AVWD…:1", cells: {...} } }, ...
  ]
}
→ { rows_written, warnings[], violations[] (on dry_run or failure), event_id }

All the operations run in one transaction and one audit event, so a single undo reverses the whole receipt. Types, required fields, references, keys, checks and ledger sums are evaluated at commit, and any failure rolls everything back with a list of every violation (not just the first). db_update_cells becomes a single-table call to the same code path.

Reading with the ledger joined in

  • db_query gains join_entry: true, which adds entry.{date, payee, accounts, amount, value_eur, effective, tags}, and expand: ["store","product"] to inline one level of references.
  • Filters on key, ref and entry columns run in Mongo with an index. Today every row is loaded and filtered in memory, with a 5,000-row cap, and line items will pass that within a year.
  • The dashboard table: source exposes the same joined fields, so view_upsert with group and agg answers "spend by store by weekday" with no new analytics tool.
  • entry_get lists the rows that explain the entry (explained_by: [{db, rows}]), and entries_list gains explained_by: "receipt_items" | "!receipt_items" to find receipts still to itemise.

The receipts template

db_templates lists ready-made schemas, and db_create {template: "receipts"} creates all five tables. They're ordinary tables afterwards, so the agent can db_alter them. Column names follow common standards (ISO 3166 country, ISO 4217 currency, GS1 GTIN), so agents in different sessions and countries end up with the same shape.

Country-specific data goes in attrs, for example:

  • Croatia: JIR, ZKI and the VAT breakdown.
  • Germany: TSE signature and transaction number.
  • US: sales tax lines and the tip on the bill.
  • Any country: loyalty savings.

The fields that analytics depends on (who, where, when, what, how much) are real columns in every country.

Making it obvious to an agent

Agents reliably read tool descriptions, and rarely read resources. So the guidance goes where they'll see it:

  • db_create description: "To attach facts to ledger entries (receipt lines, invoice splits, trip details), use an entry column plus a ledger constraint. Put shared things (stores, products) in their own table with natural row ids and point to them with ref. Put source-specific extras in a json attrs column. Check db_templates first."
  • db_templates: returns each template's schema and a short playbook, for example "find the entry with entries_list explained_by:'!receipt_items', reuse stores via db_query on stores by key, then write everything in one db_batch with dry_run first".
  • Error messages say what to do next: "receipt_items for 01M6… sum to 22.52; the entry is 22.62. Add a line of kind=rounding or discount for 0.10."
  • Table and column descriptions are returned by db_list, so the next session understands tables an earlier agent created.

"Where am I losing money"

Moneybag stores only what you paid. A price-list MCP holds what you could have paid. The agent joins them on GTIN plus store plus date, with stores.external_ids and products.external_ids holding the other system's ids. In Croatia, for example, large retailers have had to publish daily, machine-readable price lists for each shop since May 2025. No external prices are copied into the ledger, so nothing can go stale there.

Lifecycle and integrity

EventEffect
Entry reversedIts rows remain with entry.effective=false, the ledger sum is no longer enforced, and analytics drop them.
import_undo removes an entryIts rows become orphans with entry: null in joins. consistency_check lists every broken entry, ref and account value.
Delete a referenced store or productRefused, naming the rows that point to it. To merge duplicates, repoint the references with db_batch and then delete.
db_alter adds a key, check or ledger constraintExisting rows are validated first, and the change is refused with the violations listed.
db_drop on a table that other tables referenceRefused until those references are removed.

Build order

  1. The decimal, datetime, entry, account, ref, list and json types, plus descriptions. v1
  2. keys (unique index on user_id, table_id, key_hashes), checks, and the checksum functions. v1
  3. db_batch, with all constraints checked at commit, including the ledger constraint. v1
  4. Join and expand in db_query and in dashboard table: sources, with indexed filters. v1
  5. explained_by on entry_get and entries_list. v1
  6. db_templates with receipts. v1
  7. Changing a column's type, so existing string money columns can move to decimal. later

Testing plan

No test writes go to production. The integration harness only accepts databases named moneybag_test_* and drops them afterwards.

  • Unit: validation for every new type, including edge cases (decimal precision, datetime without an offset, oversized json); the checksum functions against published test vectors; key hashing; ledger sums with mixed commodities.
  • Integration (make test-integration through mcpSession):
    • A db_batch with one bad operation rolls back everything.
    • Items that don't add up are refused with the difference stated; complete items are accepted.
    • After a reversal, the ledger constraint is no longer enforced.
    • Two concurrent upserts of the same store leave one row.
    • Deleting a referenced row is refused.
    • An undo of a batch restores every table.
    • join_entry returns value_eur computed with a fixed rate_set.
    • The dashboard table: source groups by store.label and by weekday.
    • Another user can't reference your rows.
    • In a read-only session, the write tools are hidden.
  • Backward compatibility: a fixture copies the schemas of your 14 production tables (not their data), and existing db_query and db_update_cells results stay identical.
  • Agent evaluation across countries: the same template and prompt, with a Croatian Konzum receipt, a German receipt carrying a TSE signature, and a US receipt with a tip. Pass means the receipt is itemised in one batch with no new columns, and the second visit to the same store reuses the store row.
  • Production: read-only checks after deploy (db_list shows the old tables unchanged, and db_templates is listed). The first write is a real receipt you actually want stored.
